How it plays

- Between burns, the rocket's motion is calculated exactly rather than in small approximate steps. It stays on the drawn orbit forever, and escape trajectories work too.

❯ It is very good. Just a bit too fast. Explain the current time warp settings and how we could make the time/speed more adjustable

Current time warp settings

Time warp is a multiplier on the game clock. Each frame, the game converts the real time that passed into game time like this (orbi2d/game.py, in Game.update):

sim_dt = dt * self.time_warp      # TIME_WARPS = (1, 2, 4, 8)

- Keys 1–4 pick ×1, ×2, ×4 or ×8. +/− step up or down through the same list. The game always starts at ×1.
- Warped: orbital motion and main-engine thrust. Thrust adds speed per second of game time, so at ×8 one real second of burn changes your speed 8 times as much.
- Not warped: turning. It always runs in real time, so aiming feels the same at any warp.

×1 already feels fast because the base speed is set by MU = 1.5e6 and the orbit sizes, not by the warp:

┌──────────────────────────────┬──────────────────────────┐
│ Orbit size (semi-major axis) │ Time for one orbit at ×1 │
├──────────────────────────────┼──────────────────────────┤
│ 80 (lowest possible)         │ ~3.7 s                   │
├──────────────────────────────┼──────────────────────────┤
│ 200 (typical)                │ ~14.5 s                  │
├──────────────────────────────┼──────────────────────────┤
│ 330 (largest possible)       │ ~31 s                    │
└──────────────────────────────┴──────────────────────────┘

On a low orbit the ship moves about 137 units/s, which is roughly one planet-width every half second.

Ways to make it adjustable

1. Add slow-motion warps (recommended). Change the list to something like (0.25, 0.5, 1, 2, 4, 8) and start at ×0.5. The physics stays exactly the same; only the clock runs slower. It also makes precise burns easier: at ×0.25, a short tap on ↑ changes your speed 4 times less, while turning stays at full speed. The HUD would need to show values like "×0.25".

2. Smooth warp instead of fixed steps. Make +/− multiply the warp by about 1.25 each press, within limits like ×0.1 to ×16, and keep 1–4 as presets. This gives the finest control.

3. A --speed start option. Add a base speed setting, e.g. python -m orbi2d --speed 0.5, that is multiplied with the warp. Use it to set a default you like without changing the keys.

4. Change the world itself. Lowering MU slows every orbit (orbit time grows with 1/√MU). Engine power would have to drop in proportion, otherwise each burn would change the orbit much more and the 2% target would get much harder. This changes how the game feels, not just how fast it runs, so I'd use it only if you want to retune the gameplay.

I'd do 1 and 2 together: slow-motion warps, ×0.5 as the default, and smooth +/− steps, possibly with --speed from option 3 as well. It's a small change to game.py and the HUD in view.py. Should I go ahead?

❯ ctrl+c in the terminal seems to be caught. Is that a design decision or a bug?

It's a bug, not a design decision. I didn't set up any Ctrl+C handling, and this is what Python + Qt do by default.
1. Ctrl+C sends SIGINT. Python's default handler raises KeyboardInterrupt the next time Python code runs.
2. While the game runs, control sits in Qt's event loop (C++). Python code only runs during callbacks, here the 60 fps timer that calls _tick.
3. So the KeyboardInterrupt is raised inside _tick. PySide catches it, prints the traceback, and lets the event loop carry on.

Fix: after creating the QApplication, add
signal.signal(signal.SIGINT, lambda *_: app.quit())
Ctrl+C would then close the window and exit cleanly.

❯ the appimage works. The windows one I haven't properly tested yet, but when running with wine on my Ubuntu it fails with "DLL load failure while importing QtWidgets: module not found"

The first missing piece is icuuc.dll, which Qt6Core.dll needs. Every other error follows from that one: without Qt6Core, the PySide6 glue library can't load, then QtGui can't, then QtWidgets can't.

This is almost certainly a Wine limitation, not a packaging bug:
- icuuc.dll is the ICU Unicode library. On Windows 10 (1703 and later) and Windows 11 it ships as a system file in C:\Windows\System32.
- Recent Qt 6 versions for Windows use the copy Windows provides, and PyInstaller correctly leaves Windows system DLLs out of the bundle.
- Wine 9.0 doesn't provide icuuc.dll, so under Wine the chain breaks at the first link.

To settle it, the most reliable option is a smoke test on GitHub's Windows runner: launch the freshly built .exe with a hidden switch that makes it quit after 2 seconds, and fail the job unless it exits cleanly.

❯ hello. How difficult would it be to add another game mode with a solar system similar to ours, and with an orbit starting around the blue planet and a target orbit around the sun or around a big gas giant outer planet? With potential slingshot manoeuvres? I anticipate some issue with the time warp amplitude (maybe it will need to auto-adjust, like the zoom auto-adjusts). And maybe it is unrealistic to just wing a slingshot manoeuvre with our rudimentary controls?

It's quite doable. The existing physics already contains most of what's needed, slingshots included. The hard parts are the ones you suspected: scale, time warp, and giving the player enough information to aim.

What carries over almost for free
- Slingshots come built in. The Lunar Transfer mode uses patched conics. A gravity assist is exactly that: in the planet's frame a flyby is a hyperbola (you leave at the same speed you arrived, in a new direction); converted back to the sun's frame, that gives a different speed around the sun. Generalising the code to a tree of bodies (sun → planets → moons) gives slingshots with no extra physics.
- High time warp is cheap: coasting is computed exactly (analytic Kepler), so jumping hours ahead costs about the same as jumping one frame.

The real problems
1. Scale. In the real solar system, Earth is about 23,000 times smaller than its distance to the sun; a low orbit takes 90 minutes while a transfer to Jupiter takes 2.7 years. I'd recommend a compressed system "like ours", the way KSP shrinks its planets.
2. Time warp: your instinct is right, it has to adjust itself. Your choice becomes a ceiling; warp drops as a predicted SOI crossing approaches, depends on the current orbit's period, and is limited while burning.
3. Can you wing a slingshot? Not with today's prediction, but with better tools, yes: chained prediction (leaving the planet → around the sun → flyby → the orbit you leave on), closest-approach markers, and optionally planned burns (KSP's "maneuver nodes").

Effort, in steps:
1. Generalise the bodies, chained prediction, a camera that can focus on any body with logarithmic zoom, automatic time warp, and a "Solar System" mode.
2. Make slingshots playable: closest-approach markers, levels or scoring where a slingshot clearly pays off.
3. Optionally, planned burns.
