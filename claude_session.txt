It needs PySide6, which is already installed here. All 14 physics tests pass, and I rendered a test screenshot offscreen to check the drawing. I haven't played it with a real keyboard, so the feel of the controls is still untested.

How it plays
- The planet sits in the middle, the rocket starts on a random orbit (solid blue line), and the target orbit is a dashed green line. A new level gets a new random pair.
- ←/→ fire the side thrusters, which only turn the ship. ↑ fires the main engine.
- The blue orbit is recalculated and redrawn every frame while the engine fires. Periapsis and apoapsis are marked "Pe" and "Ap" on both orbits.
- A yellow circle next to the ship shows the direction you're moving (prograde) and a red ✕ shows the opposite direction (retrograde), so you can see which way to point to slow down.
- The screen also shows the numbers for your orbit and the target, how far apart they are, and how much speed change (Δv) you've spent. It warns you if you're heading into the planet or out of orbit.
- You lose if you hit the planet or fly too far away.

How the orbital mechanics work
- Between burns, the rocket's motion is calculated exactly rather than in small approximate steps. It stays on the drawn orbit forever, and escape trajectories work too.
- A burn is applied as many tiny speed changes along the ship's nose direction, and the orbit is recalculated from the resulting position and velocity. So a burn in any direction at any point gives the real result. The tests confirm the apsis behaviour you described, and also that a sideways burn tilts the orbit.

Choices I made that you may want to change
- Win rule: the engine must be off, and the two orbit curves must be within 2% of each other in every direction. Measuring the gap between the curves means near-circular orbits are judged fairly. Direction of travel doesn't count.
- Extras you didn't ask for:
  - Holding Shift gives 10% thrust and slower turning. A full-power burn is too coarse to land inside 2%, so I think this is needed.
  - Time warp on keys 1–4, so you don't wait 20+ seconds for the far side of a big orbit.
  - Pause (P) and new level (R).
  - The view zooms out automatically when your orbit grows.
- Thrust power, turn speed, the 2% tolerance and orbit sizes are all set at the top of orbi2d/game.py.

❯ It is very good. Just a bit too fast. Explain the current time warp settings and how we could make the time/speed more adjustable

Current time warp settings

Time warp is a multiplier on the game clock. Each frame, the game converts the real time that passed into game time like this (orbi2d/game.py, in Game.update):

sim_dt = dt * self.time_warp      # TIME_WARPS = (1, 2, 4, 8)

- Keys 1–4 pick ×1, ×2, ×4 or ×8. +/− step up or down through the same list. The game always starts at ×1.
- Warped: orbital motion and main-engine thrust. Thrust adds speed per second of game time, so at ×8 one real second of burn changes your speed 8 times as much.
- Not warped: turning. It always runs in real time, so aiming feels the same at any warp.

×1 already feels fast because the base speed is set by MU = 1.5e6 and the orbit sizes, not by the warp:

┌──────────────────────────────┬──────────────────────────┐
│ Orbit size (semi-major axis) │ Time for one orbit at ×1 │
├──────────────────────────────┼──────────────────────────┤
│ 80 (lowest possible)         │ ~3.7 s                   │
├──────────────────────────────┼──────────────────────────┤
│ 200 (typical)                │ ~14.5 s                  │
├──────────────────────────────┼──────────────────────────┤
│ 330 (largest possible)       │ ~31 s                    │
└──────────────────────────────┴──────────────────────────┘

On a low orbit the ship moves about 137 units/s, which is roughly one planet-width every half second.

Ways to make it adjustable

1. Add slow-motion warps (recommended). Change the list to something like (0.25, 0.5, 1, 2, 4, 8) and start at ×0.5. The physics stays exactly the same; only the clock runs slower. It also makes precise burns easier: at ×0.25, a short tap on ↑ changes your speed 4 times less, while turning stays at full speed. The HUD would need to show values like "×0.25".

2. Smooth warp instead of fixed steps. Make +/− multiply the warp by about 1.25 each press, within limits like ×0.1 to ×16, and keep 1–4 as presets. This gives the finest control.

3. A --speed start option. Add a base speed setting, e.g. python -m orbi2d --speed 0.5, that is multiplied with the warp. Use it to set a default you like without changing the keys.

4. Change the world itself. Lowering MU slows every orbit (orbit time grows with 1/√MU). Engine power would have to drop in proportion, otherwise each burn would change the orbit much more and the 2% target would get much harder. This changes how the game feels, not just how fast it runs, so I'd use it only if you want to retune the gameplay.

I'd do 1 and 2 together: slow-motion warps, ×0.5 as the default, and smooth +/− steps, possibly with --speed from option 3 as well. It's a small change to game.py and the HUD in view.py. Should I go ahead?

1. Decide two things
- Name: orbi2d, unless you want something else.
- Public or private: a public repo is visible to everyone, and that includes claude_session.txt. I checked it earlier and it has no secrets in it, but make sure you're happy for people to read it.

2. Create the repo and push

From the project folder, run:

gh repo create orbi2d --public --source=. --remote=origin --push \
  --description "2D orbital mechanics game: steer a rocket onto a target orbit (Python + Qt)"

- Use --private instead of --public if you want it private.
- --source=. --remote=origin --push creates the repo under your account and adds it to this folder as the remote origin. It then pushes main with all 3 commits and sets it up so later git push / git pull work with no extra arguments.

3. Check it worked

git remote -v          # should show git@github.com:PiRK/orbi2d.git
gh repo view --web     # opens the repo in your browser

GitHub should show "MIT License" next to the repo, because it recognises the LICENSE file.

4. Later changes

git push

The step 2 command stays the same. When it pushes, master will be the only branch, so GitHub will make it the repo's default branch automatically. You can check this after the push with:
